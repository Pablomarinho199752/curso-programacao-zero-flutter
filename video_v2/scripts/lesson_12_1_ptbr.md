# Aula 12.1 — Desenvolvimento independente: descobrir, construir e provar

## Padrão de produção
- Voz: Maya
- Idioma: português do Brasil (pt-BR)
- Velocidade: 0,80
- Duração-alvo: 3 a 5 minutos
- Resolução: 1920×1080

## Narração

Nesta aula, você chega a uma parte muito importante do curso: aprender a começar uma tarefa mesmo quando ainda não sabe exatamente como implementá-la.

Autonomia em programação não significa saber todos os comandos de memória. Também não significa nunca precisar pesquisar. Ser independente significa conseguir transformar uma ideia em passos, descobrir o que falta, testar pequenas hipóteses e continuar avançando.

Imagine que alguém diga: “crie um aplicativo completo”. Isso é amplo demais. Antes do código, precisamos transformar a ideia em requisitos observáveis.

Um requisito verificável diz algo que podemos testar. Por exemplo: o usuário consegue cadastrar uma tarefa. A tarefa permanece depois que o programa é fechado. O usuário consegue marcar a tarefa como concluída.

Agora já temos comportamentos que podem ser provados. Isso é muito melhor do que simplesmente escrever “fazer um app bonito e completo”.

Depois dos requisitos, identifique as dúvidas técnicas reais. Talvez você saiba criar uma lista, mas ainda não saiba salvar os dados. Em vez de pesquisar “como fazer meu aplicativo inteiro”, crie uma pergunta menor: “como salvar uma lista em um arquivo JSON usando Python?”.

Quanto mais específica a pergunta, mais fácil avaliar a documentação e testar uma resposta.

A pesquisa técnica deve começar por fontes confiáveis, principalmente documentação oficial quando ela existir. Leia apenas o necessário para responder à pergunta atual. Depois crie o menor experimento possível.

Se você quer descobrir como uma biblioteca faz uma requisição, não construa a aplicação inteira de uma vez. Faça uma requisição simples. Mostre a resposta. Confirme que entendeu. Depois integre ao projeto.

Esse ciclo reduz muito a confusão: requisito mínimo, dúvida específica, pesquisa, experimento pequeno, implementação, teste e registro da decisão.

Agora observe uma estratégia ruim: objetivo “criar um app completo”; plano “pesquisar na internet e copiar o primeiro código que aparecer”. Mesmo que esse código funcione, você não sabe se ele resolve seu requisito, se é adequado ao seu projeto nem como corrigir quando algo mudar.

Copiar sem entender cria dependência. Pesquisar para responder uma pergunta cria aprendizado.

Seu desafio será escolher uma ideia pequena que você nunca implementou. Escreva três requisitos verificáveis. Depois anote uma dúvida técnica real e explique como testaria a primeira versão.

Por exemplo, se sua ideia é um rastreador de hábitos, um requisito pode ser cadastrar um hábito. Outro pode ser registrar a conclusão do dia. Outro pode ser mostrar quantos dias foram concluídos. Sua dúvida talvez seja como armazenar datas. Então faça um experimento mínimo apenas com datas antes de construir o resto.

No projeto final, escolha algo que tenha valor para você. Não haverá código pronto fornecido pelo curso. Primeiro escreva os requisitos. Liste riscos e tecnologias que você ainda não domina. Defina como vai pesquisar. Planeje como provar que cada requisito funciona. Depois implemente a menor versão funcional.

Quando encontrar um erro, volte ao método que você praticou durante o curso: reproduza, observe, crie uma hipótese, altere uma coisa de cada vez e teste novamente.

Quando encontrar algo desconhecido, não conclua que ainda “não sabe programar”. Transforme o desconhecido em uma pergunta concreta. Essa é uma habilidade central de quem programa profissionalmente.

Ao final deste módulo, o objetivo não é você saber tudo. É você conseguir dizer: eu não sei esta parte ainda, mas sei como descobrir, testar e decidir o próximo passo.

Essa é a passagem mais importante do curso: sair de alguém que espera uma solução pronta para alguém que consegue planejar, pesquisar, construir, provar e melhorar sua própria solução.

## Cenas previstas
1. Tarefa vaga “crie um app” virando requisitos claros.
2. Requisitos verificáveis com caixas de teste.
3. Dúvida grande virando pergunta técnica específica.
4. Documentação → experimento mínimo.
5. Ciclo requisito → pesquisa → teste → implementação.
6. Comparação “copiar primeiro código” versus “pesquisar para responder uma pergunta”.
7. Exemplo de rastreador de hábitos.
8. Planejamento do projeto final.
9. Fechamento visual mostrando autonomia e próximo passo.
